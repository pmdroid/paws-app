# Paws glossary

Domain words used in code, issues and reviews. Each term names one concept; code that means the concept uses the term.

| Term                   | Meaning                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Item**               | One delegation of one Linear issue. Has an owner and an optional Project, owns exactly one Linear session. At most one Item per issue is active; delegating the issue again creates a new Item. Row: `work_item`.                                                                                                                                                                                          |
| **Project**            | The Linear project an issue belongs to. The issue page shows it and the Issues page filters by it. Paws keeps no project of its own: work starts when someone delegates an issue, or a parent issue, in Linear.                                                                                                                                                                                            |
| **Parent delegation**  | A delegated parent issue whose sub-issues each run in their own Linear session and their own Run. A sub-issue's session opens once its Blocks are satisfied, and the parent's session ends with one summary. The parent's delegation id groups the sub-issues; each sub-issue keeps its own delegation. Rows: `parent_delegation`, `parent_delegation_issue`.                                              |
| **Run**                | One agent attempt on an Item. Implementation, review and fix attempts are Runs. Row: `run`.                                                                                                                                                                                                                                                                                                                |
| **Block**              | A Linear "blocks" relation between two issues, stored once for the workspace. Row: `task_block`.                                                                                                                                                                                                                                                                                                           |
| **Block satisfied**    | The blocker's latest Item is `merged`, or `completed` when that Item's task mode is answer or artifact. Decided by one predicate in `src/core`.                                                                                                                                                                                                                                                            |
| **Admission**          | Whether an Item may start or merge, answered in one place. `src/scheduler` composes it: readiness (Blocks, pending delegation changes, snapshot freshness) from `src/intake`, plus its own fair order, owner cap and free Slots. Exposed as `canStart`, `canMerge` and `dispatch`. Publish readiness is separate: it is asynchronous and bound to the candidate, and lives in `src/intake/publication.ts`. |
| **Reservation**        | The durable `scheduler_admission` row that `dispatch` writes with the start job in one transaction. The job claim starts an Item only against its Reservation.                                                                                                                                                                                                                                             |
| **Closeout**           | The verification of a candidate commit. A rejected candidate returns to the agent with findings; an accepted one may be published.                                                                                                                                                                                                                                                                         |
| **Restart**            | `restart(item, handoff)`: the one operation that sends an Item back to the agent. Cancels the Item's pending jobs, releases its Slot and merge lane, records the handoff with a reason (`findings`, `ci`, `review`, `conflict`, `follow_up`, `answer`) and enters `queued`. Keeps the Run and the Linear session. In `src/loop`.                                                                           |
| **Lifecycle event**    | The `transition()` event a `work_item_event` row records. It names the operation that happened: an operation without an agent turn, such as reusing accepted work or re-verifying after an approval, takes one direct edge instead of passing through `running`. Older rows may name retired events, listed in `RETIRED_WORK_ITEM_EVENTS`.                                                                 |
| **Ask**                | `ask(item, question)`: the one operation that asks a person. Opens one Linear elicitation in the Item's session and enters `awaiting_input`; the answer is the next handoff. The only activity that reopens a session after its pull request response. In `src/loop`.                                                                                                                                      |
| **Accept row**         | Closeout's record that it accepted head S under policy digest D, with any bypass rows for S. The only thing that makes S mergeable. A new commit, a rebase or a policy change needs a new accept row.                                                                                                                                                                                                      |
| **mergeable(S)**       | The predicate the merge lane checks for head S while it holds the repository lock: the pull request head is S, S contains the current main, an accept row exists for S under the current policy digest, CI is green for S, no review thread is unresolved and branch protection is satisfied. When it holds, the lane squashes with expected head S. In `src/merge`.                                       |
| **Fix round**          | One Restart caused by Closeout findings, red CI or a changes-requested review. Counted per Item against `retry.fix_rounds_per_item` (default 3) since the latest reply from a person; then Paws asks.                                                                                                                                                                                                      |
| **Attempts per check** | `retry.attempts_per_check` (default 3): how many failed attempts one Closeout check gets, on the agent side and the Paws side. A check that reaches it is exhausted, and Paws asks.                                                                                                                                                                                                                        |
| **Rebase return**      | One Restart with reason `conflict`, after a rebase in the merge lane conflicts. Three in a row on a known main commit, six in any rolling hour, then Paws asks. A newer main does not refill the budget; a person's reply does.                                                                                                                                                                            |
| **Runner**             | An enrolled Linux runner that takes signed commands, runs the agent, and reports events and results.                                                                                                                                                                                                                                                                                                       |
| **Slot**               | Capacity for one simultaneous Run on a Runner. A Run holds its Slot from its first command through Closeout.                                                                                                                                                                                                                                                                                               |

## User-facing vocabulary

Use these words in dashboard copy and Linear responses. Existing API fields, routes, configuration keys, and stored identifiers keep their names.

| Chosen word     | Use instead of | Meaning                                                                                                 |
| --------------- | -------------- | ------------------------------------------------------------------------------------------------------- |
| Item            | Task           | One delegation of a Linear issue.                                                                       |
| Runner          | Host           | The Linux runner that executes delegated work. The Paws server is the process that coordinates runners. |
| Slots           | Concurrency    | How many Runs a Runner can execute at once. One Run occupies one Slot.                                  |
| Closeout result | Verdict        | The outcome of Closeout verification for a candidate commit.                                            |
| Enrolled        | Paired         | A Runner registered with a Paws workspace. Use "enroll" for the action.                                 |
