# Improvement review API

The improvement inbox lists daily findings and weekly retro proposals together. Each improvement carries one review decision, tied to one immutable proposal version. `src/improvements` serves the shared review routes; `src/retros/http.ts` serves the retro history, report, evidence and download routes.

Every route checks active workspace membership on each request before it reads anything. The reader's Linear sessions (see [Dashboard API](dashboard-api.md#authorization)) decide what is visible. A daily item needs every member finding in a readable session. A member reads the repositories mapped to their Linear teams; an administrator reads every workspace repository. A retro item needs all of its saved evidence in readable sessions and readable repositories. An item outside that set answers the same 404 as an unknown id. Lists, counts and repository filters are built only from visible items. Responses are `no-store`. A mutation passes the server's origin and CSRF checks and is audited.

## Inbox

| Route                                                     | Does                                                                                                                                                                                                                                       |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/improvements`                                   | Visible items, filtered by `source` (`daily`, `weekly`), `repository` and `state` (`needs_review`, `pending`, `linked`, `rejected`), with `cursor` and `limit` (at most 100). Returns `counts` over all visible items.                     |
| `GET /api/improvements/<id>`                              | The item with its proposal history, decisions, criterion annotations and saved evidence. Also the Linear teams this reviewer may file to (`destinations`) and up to ten known issues already linked in the same repository (`candidates`). |
| `POST /api/improvements/<id>/decision`                    | `{ expectedVersion, decision }`: accept, reject with a reason, or reopen.                                                                                                                                                                  |
| `POST /api/improvements/<id>/deliveries/<id>/retry`       | Puts a failed delivery back in the queue under the same id.                                                                                                                                                                                |
| `POST /api/improvements/<id>/deliveries/<id>/cancel`      | Drops an evidence comment that is blocked after its link succeeded and that never reserved its comment id. The link stays and the decision records no comment. Otherwise 409 `cancel_comment`.                                             |
| `POST /api/improvements/<id>/deliveries/<id>/destination` | `{ teamId }`: files a create that is blocked on a lost team mapping to another mapped team. Refused (409 `destination_frozen`) once Paws may have sent the issue.                                                                          |

An accept names `proposalVersion` (the latest one) and exactly one intent:

- `{ kind: "create", teamId }`: the team must be mapped to the item's repository, and a member must belong to it. If the item already has an issue, this answers 409 `known_issue`: link that issue instead.
- `{ kind: "link", issue, addEvidenceComment?, allowClosed? }`: Paws reads the issue from Linear first. A missing issue answers 400. An issue in a team outside the repository's mapping answers 409 `team_mismatch`. A closed issue answers 409 `issue_closed` unless `allowClosed` is set, and linking never reopens it. If Linear is unavailable, nothing is saved and the route answers 503. Only `addEvidenceComment: true` queues an evidence comment; a plain link posts nothing.

A link waits for Linear before it decides, so the accept transaction reloads the reviewer's membership, teams and repositories and checks the destination again. Access lost during the lookup refuses the decision. An accept writes the actor, time, chosen intent, destination and exact proposal text to the delivery, all in one transaction. If no criterion was ever recorded, the reviewer must send `verificationCriterion`. A daily finding has none until then. The criterion becomes a versioned annotation and the source proposal is left as it was. A reject records its reason and creates no delivery. Linear writes happen later, in the delivery handler described under [Delivery](#delivery).

### Conflicts and retries

- Sending the decision already recorded again answers 200 with `status: "unchanged"`. That covers duplicate clicks and repeated requests. A link matches by the issue id or identifier it was given. A `verificationCriterion` that differs from the saved one is a new decision, not a repeat.
- A different decision with an old `expectedVersion` answers 409 `stale` and returns the current decision. It never overwrites another reviewer.
- An accepted item cannot be rejected (409 `accepted`): its delivery may already have reached Linear. It can be reopened only while nothing reached Linear: it is a link whose `link_issue` delivery is blocked, and no delivery succeeded, is claimed, is `unknown` or reserved a Linear id. Reopening deletes those undelivered deliveries and their attempts in the same transaction, and the item returns to `needs_review` for a new choice. Otherwise reopen answers 409 `accepted`. A create is never reopened, because its issue id may already exist in Linear.
- If a Findings group action or an individual "File issue" on a finding already claimed, filed or added any of an item's findings, the inbox accept answers 409 `legacy`. An individual filing records a durable claim before it calls Linear, so a filing still in flight counts. An individual filing counts even when a dismissed group covers the finding. The other way round, a group File, Add or Dismiss, a single-finding dismissal, or an individual filing on findings the inbox accepted answers 409.
- A delivery reports `pending`, `retryable` (failed), `unknown` or `succeeded`, with `blocked`, `nextAttemptAt` and `recovery` (`retry`, `choose_destination`, `reopen`, `cancel_comment` or null). A link blocked as `destination`, `conflict` or `unavailable` offers `reopen`; an evidence comment blocked for the same reasons after its link succeeded offers `cancel_comment`. Only a succeeded delivery has a canonical issue. Retrying a failed delivery keeps the item accepted. An `unknown` delivery answers 409 `reconciling` while the handler still checks it on its own; once it is blocked, retry clears the block and it stays `unknown`.

## Delivery

`src/improvements/delivery.ts` runs every 15 seconds. It claims one delivery at a time with a lease (`claimImprovementDelivery`); only the owner and attempt that hold the claim can settle it, so two workers or a restarted process cannot both write. It runs creates and links before evidence comments, and an evidence comment waits until its link succeeded. Each workspace delivers only through the Linear connection of its own organization; any other workspace's delivery is blocked as `workspace`.

- **Create.** The issue id is a UUID derived from the workspace, the improvement and the operation. The handler first looks that id up in Linear. It records a found issue only if it is in the frozen team and its description carries the Paws reference `paws-improvement:<workspace>:<improvement>:<repository>`; otherwise the delivery is blocked as `conflict` and nothing is linked. Not found, the handler stores the id on the delivery, then calls `issueCreate` with it, in the team's Triage state (Backlog without Triage), with the `review finding` label for a daily finding or `paws retro` for a weekly retro, and no delegate. The body is built from the content frozen at acceptance: repository and area, source kind, action step, problem, remaining work, verification criterion, evidence counts, a link to the improvement in the dashboard, who accepted it, and the Paws reference.
- **Link.** Acceptance freezes the issue's team, which the reviewer was authorized for. The handler reads the issue and records it only if it is still in that team and the team is still mapped to the repository. It writes nothing to Linear. A missing issue blocks as `unavailable`; a moved issue or unmapped team as `destination`; an issue closed since acceptance, when it was accepted open, as `conflict`, so the reviewer reopens the item and chooses again. That covers links accepted before Paws froze the team, which block as `destination`. A link never turns into a create.
- **Evidence comment.** Same pattern as a create, with a comment id derived the same way. Before posting, the issue passes the same checks as a link; a comment refused there can be cancelled while its link stays.

A succeeded create or link saves the Linear id, identifier and URL on the improvement and marks its open daily findings filed with that identifier, in the same transaction. Later proposals attached to the improvement reuse that issue; nothing files a second one.

Once the id is stored, an attempt that does not confirm the write leaves the delivery `unknown`: a timeout, a lost response or an empty lookup is not proof of absence. The next attempt looks up the same id; a second create with that id cannot make a second issue. A rate limit or a failed read waits with exponential backoff (30 seconds doubling up to an hour, or longer when Linear names a retry time). Eight attempts without a result block the delivery as `attempts`. Revoked Linear access blocks it as `unauthorized`. A create whose team is no longer mapped blocks as `destination`. Before the id was ever stored, `POST .../destination` may move it to another mapped team, keeping the same id. After that, its team cannot change: the database refuses it. Every block keeps the accepted decision and waits for a person.

## Follow-through

Filing or linking an issue starts follow-through; it does not resolve the improvement. `src/improvements/outcomes.ts` builds one view per accepted item from rows Paws already keeps: the confirmed issue, what Paws last read about it in Linear, the Paws work item for that issue with its pull request and merge fact, and the outcome history. Review, delivery, implementation and verification stay separate fields.

| Route                                       | Does                                                                                                                                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/improvements/attention`           | Counts (`newReview`, `filingErrors`, `needsAttention`, `verificationDue`), each visible item's attention state, batched activity entries and metrics.          |
| `GET /api/improvements/<id>/follow-through` | The follow-through view with its outcome history and audited actions.                                                                                          |
| `POST /api/improvements/<id>/delegate`      | `{ expectedVersion }`: delegates the confirmed issue to Paws.                                                                                                  |
| `POST /api/improvements/<id>/verification`  | `{ expectedVersion, outcome, check, result, revision?, deployment?, evidence }`: records `verified` or `contradicted`.                                         |
| `POST /api/improvements/<id>/criterion`     | `{ expectedVersion, criterion }`: annotates the verification criterion of an accepted item, for migrated items that have none. The proposal is left as it was. |
| `POST /api/improvements/<id>/recovery`      | `{ expectedVersion, choice, reason }`: `acknowledge`, `redelegate` or `return_to_review`, when the view offers it.                                             |

Attention is one of `needs_review`, `rejected`, `accepted_unfiled`, `filing_failed`, `ready_to_delegate`, `working`, `blocked`, `awaiting_verification`, `verified`, `verification_stale`, `canceled`, `unavailable`, `stale_sync` or `closed`.

- **Implementation.** A Paws work item decides it: `merged`, `canceled` (including a cancelled run with a closed pull request), `completed`, `blocked` (failed, waiting for an answer, paused or manual) or `in_progress`. Without one, only a terminal Linear state counts: Done is `completed`, Canceled or Duplicate is `canceled`, anything else is `not_started`. Paws never infers running work from a Linear status. Merged and Done both make verification due; neither verifies.
- **Linear reads.** Every 10 minutes the sweep reads up to 50 linked issues, the least recently checked first, through the organization's own Linear connection. Each improvement's check time (`improvement_sweep`) is recorded before its read, so a read that keeps failing or a workspace without a connection cannot hold up the others. A read is stored only if it began after the stored one and is for the issue the improvement links now, so an older read or one for a replaced issue cannot replace a newer one. A workspace without a Linear connection records `unavailable`. Missing, unauthorized or unavailable keeps the last confirmed time and shows `unavailable`. No read for 6 hours shows `stale_sync`. `settle` in `outcomes.ts` is the one step that records what the current state implies: the followed work, each implementation change in the outcome history, and verification becoming due or contradicted. The sweep runs it, and so does every delegate, verification, criterion and recovery request before it checks the expected version. A verification transition raises the version, so contrary evidence found since a form opened answers 409 `stale` even before the next sweep. Every response is read after the request's own writes, so its version is the one the next request needs. It never writes to Linear.
- **Followed work.** Each improvement follows one stored Paws work item (`improvement_work`); every view, delegation, verification, recovery and sweep reads that binding instead of searching by issue. Only `followWork` in `outcomes.ts` writes it: it follows the newest work item for the issue in the improvement's repository that was created after the issue was confirmed, or that was still active then. Work that finished before the link, including work from before a return to review, never counts. A newer run on the issue replaces the followed work once that work has ended, merged or completed; a replaced verification becomes stale. Each bind is a `follow_work` audit row that raises the version, so a form opened against the earlier work answers 409 `stale`. Work in another repository is never followed. An acknowledged item does not bind new work, and returning an item to review drops its binding.
- **Delegate.** Offered only for a confirmed, open issue with no delegate and no Paws work item. A delegate already set, an existing work item, or another improvement's delegation of the same issue is recorded as `existing` and shown; nothing starts. Another improvement's delegation counts while its lease is live, or until work it started on the issue has ended; after that the issue can be redelegated. Otherwise Paws reads the issue again and checks the team it is in now against the reviewer's teams and the repository mapping, takes a 60-second lease and starts a Linear agent session on the issue, the same start the dashboard uses. Intake then applies its normal access checks and capacity waits. A repeated click answers `unchanged` or `in_progress`. A lease that expires without an answer settles as `existing` if a work item for the issue was created after the request, otherwise `failed` with a retry. A newly created issue stays undelegated until someone delegates it.
- **Verification.** Needs a criterion, merged or completed work, the check and its result, and a revision or deployed version. A Closeout check counts only if it ran on this improvement's work item at the head Closeout accepted, passed, and the criterion names its step id or command as a whole word; its head becomes the revision. A human attestation may add an HTTPS URL; the URL is never the proof. A revision must match the merged commit Paws recorded. A finding that disappears or a quiet retro never verifies. A daily finding seen again after verification, or verified work whose Paws work or Linear issue reopens, makes verification `contradicted` (`verification_stale`) without reopening the issue or starting work.
- **Recovery.** `acknowledge` (canceled, unavailable or blocked items) records the outcome as closed without a fix; it stays closed, whatever is recorded later, until someone returns it to review. `redelegate` starts a new session when the Paws work was cancelled and the issue is still open; failed work is still active to intake, so it offers acknowledge or return to review instead. `return_to_review`, offered for any linked item whose deliveries settled and whose Paws work is not still running, saves the issue, deliveries, work and delegation in the audit row, clears the link and returns the item to review. An item whose own issue Paws created cannot then be created again (409 `recovered_issue`); link an issue instead.

Each mutation checks membership and repository access again after its body is read, requires `expectedVersion` and answers 409 `stale` with the current view when it does not match, and writes an immutable audit row with actor, time, detail and prior state. Activity entries batch items by kind (review, filing, work, verification); an entry's key changes only when a durable transition joins it. Metrics count time to decision, items awaiting filing or delegation, completed implementations and verified outcomes. They name no people.

## Dashboard

The Improvements page under Work (`src/dashboard/src/client/improvements-page.ts`) reads only these routes and `GET /api/retros/schedule`; it adds nothing to another page's resource. Its sidebar entry shows `counts.total` from `GET /api/improvements/attention`.

- `/dashboard/improvements` lists the inbox with Source (all, daily findings, weekly retros), Repository and State filters kept in the query, and pages through `nextCursor`. Above the list, each source shows its own run: the last daily grouping run, and the weekly retro's schedule state (queued, waiting for a runner, generating, failed with Retry generation, no recurring patterns, or the first retro with Run retro).
- `/dashboard/improvements/<id>` opens one item beside the list (on a phone, instead of it, with an All improvements link back to the same filters). It shows the source, problem, evidence, intended change, criterion, existing issues in the repository and the next action. Create issue, Link existing issue (the default when the repository already has linked work, with an explicit evidence comment choice) and Reject with a reason post the decision. Accepted items show each delivery: filing, retrying, checking with Linear for an unknown outcome, or needing a recovery. Once the issue is confirmed, follow-through shows the last confirmed read, implementation and verification separately, a Delegate to Paws button only when offered, the verification form once work merged or completed, and the recovery choices.
- An item whose findings a Findings action filed, added, claimed or dismissed is read-only: the page shows the earlier action and its issue with a link to Findings, offers no decision, reopen, delegation or follow-through, and its attention is `closed`, so it is not counted. One client function, `improvementStage` in `src/dashboard/src/client/improvement-stage.ts`, decides which actions each item allows, for both rendering and sending.
- `/dashboard/improvements/reports/<id>` shows a frozen report: its windows, numbers, at most five patterns with counts and a link to each inbox item, worked well, notes and coverage gaps, or its generation state. With full access it also shows the settings it froze from `/settings`. Beside each pattern's frozen claims and decision, a separate "Now" block shows the improvement's current attention, confirmed issue, last Linear read, implementation and verification, or says the reader cannot see it; it never rewrites the report. `?item=<item>` selects a pattern and loads its saved excerpts from the evidence route, so reload, Back/Forward and a shared link keep the report and the item; an item the reader cannot read shows "Item not available" and an unknown or hidden retro the history recovery. With full access the Frozen files section labels the digest's window and coverage (sessions, counted records and earlier records kept only as bounded prompt context) and downloads the digest, report and rendered prompt, and says how much of the digest the bounded prompt gave the agent; a file whose record outlived it shows as unavailable, and a 403 after access was lost shows the refusal and nothing from the file. Paws sets no retention period for retros, and the page does not promise one.
- `/dashboard/improvements/history` lists retros newest period first, with sessions, and with full access the settings revision and profile, the review state (generation state, no recurring patterns, to review or reviewed), expired or incomplete evidence, an unavailable digest, a partial view, and the issues linked from its items. "No reports yet" is the empty state.
- `/dashboard/improvements/settings` links daily grouping settings, shows the retro schedule and holds the retro settings form.
- The retro settings form (`src/dashboard/src/client/retro-settings.ts`) groups Agent, Prompt, Sessions and output, Schedule and Run limits. It reads `GET /api/retros/settings`, model and effort choices from `GET /api/runners/models`, previews the draft with `POST /api/retros/preview` and saves every field in one `PUT /api/retros/settings` with `expectedRevision`. Changing the agent clears model and effort; changing the model clears an effort it does not offer; a saved choice no runner offers stays selected and is marked unavailable. Variables insert at the editor's cursor and keep focus there. Restore default prompt changes the draft only. The draft survives tab changes and is dropped on a workspace switch or a 401 or 403. A preview answer for an older draft is marked stale. A 409 keeps the draft and offers to save over the new revision or load it; a 503 `catalog_unavailable` is shown as runner availability, apart from invalid fields. Members see the saved settings read-only.

The page polls the open tab every 5 seconds while it is visible: the list and attention on Review, and the open item until it is rejected, verified or closed with settled deliveries; a report only until it is generated; history only while a retro is generating. Evidence loads with the item and is never polled. A response is applied only if no navigation, filter change or mutation happened since it was sent, and an item or follow-through never replaces one with a higher `version`. Buttons are disabled while a mutation is in flight; a 409 shows the current decision instead of retrying.

`bun run verify:improvements-ui <dir>` runs the production server over the fixture in `test/improvement-fixtures.ts` with fake Linear adapters and drives Chromium at 1440 and 390 pixels in both themes: no horizontal overflow and no control under 44 pixels, phone back navigation, old `/retros` and `/status` links, a decision from another tab, a lost create response reconciled to one issue, explicit delegation, merged awaiting verification, verified, failed and waiting generation, and no requests while the tab is hidden.

`bun run verify:retro-settings-ui <dir>` drives the retro settings form the same way, with the production settings and preview handlers and a stubbed runner catalog: agent and model compatibility, prompt variables, validation, preview and Restore default, unsaved edits across tabs, saved values after reload, a failed save and a revision conflict keeping the draft, invalid limits, pause and resume, a saved model no runner offers, repository denial, a report keeping its frozen settings, and the member read-only view.

## Retros

| Route                                                       | Does                                                                                                                                                            |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/retros/history`                                   | Retros with at least one visible item or full access, newest window end first, with `cursor` and `limit` (at most 50).                                          |
| `GET /api/retros/reports/<id>`                              | The frozen report. With partial access, it has visible items only and no numbers, prior work, other repositories' windows, coverage gaps or generation errors.  |
| `GET /api/retros/reports/<id>/items/<item>/evidence`        | The item's excerpts from the saved evidence. Mutable session history is never queried.                                                                          |
| `GET /api/retros/reports/<id>/digest`, `/report`, `/prompt` | Download the frozen digest, the rendered report or the rendered prompt.                                                                                         |
| `GET /api/retros/reports/<id>/settings`                     | The settings revision, prompt template, resolved agent, model and effort, repositories and limits the retro froze when it started. Full access only.            |
| `POST /api/retros/preview`                                  | Renders an unsaved `prompt` with its `outputLimits` against the newest digest the admin reads in full, or a sample. Admins only; runs no agent, stores nothing. |

A history entry carries review counts and each visible item's improvement and confirmed issue. Only with full access does it add the settings revision, the frozen profile (`agent`, `model`, `effort`; a null effort is the agent's default), the digest's size (`sessions`, `counted`, `context`), the number of patterns, `evidence` (`complete`, `incomplete`, or `expired` when a source's retention ran out) and each file's state (`stored`, `unavailable` when its record outlived the file, or `none`). It never carries excerpts. `nextCursor` names the last retro shown, so a retro added between pages neither repeats nor skips one. The report adds `current`: each visible item's follow-through now, or null when the improvement is not in the reader's inbox.

The rendered prompt embeds the full digest. So all three downloads need full access: every included repository readable by the member and every session in the digest. Partial access answers 403 `partial_access`, without naming what is missing. Each download is audited.
