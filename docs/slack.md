# Slack

A workspace admin connects one Slack workspace to a Paws workspace in **Workspace › Integrations**. This installs the Paws app in Slack. It gives Slack users no Paws membership, repository access or permission to start work, and Paws reads no private messages except those sent to the app. Paws reads only the channel messages that mention it, and replies from linked members in threads it was already mentioned in, in the one channel set up below.

## Create the Slack app

The quickest way is the manifest in [`deploy/slack/manifest.yaml`](../deploy/slack/manifest.yaml). On [api.slack.com/apps](https://api.slack.com/apps), choose **Create New App › From a manifest**, pick the Slack workspace, and paste the file after replacing `https://paws.example.com` with your Paws URL. It sets up everything in steps 1 and 2, so continue with step 3. Slack checks the events URL as soon as the app is created; Paws answers that check before you have saved the signing secret, and refuses every other request until you have. To set the app up by hand instead:

1. On [api.slack.com/apps](https://api.slack.com/apps), create an app. Under **OAuth & Permissions**, add the redirect URL `https://<paws>/oauth/slack/callback` and the bot scopes below. Turn on **Agents & AI Apps** and the **Messages Tab** in **App Home**.
2. Under **Event Subscriptions**, set the request URL `https://<paws>/webhooks/slack` and subscribe to the bot events `app_mention`, `message.channels`, `message.im`, `assistant_thread_started`, `agent_session_stopped`, `app_uninstalled` and `tokens_revoked`. Under **Interactivity & Shortcuts**, turn on **Interactivity** and set the same request URL `https://<paws>/webhooks/slack`; Paws's **Stop** button needs it. Turn on **Manage Distribution** to install it in more than one Slack workspace.
3. Set `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET` and `SLACK_SIGNING_SECRET` on the server, or enter them in the dashboard. Set `SLACK_APP_ID` so Paws refuses any other app. **Token Rotation** may be on or off; with it on, Paws refreshes a workspace's token when it is about to expire. Slack must reach Paws over HTTPS.

## Scopes

Channel threads need `app_mentions:read`, `channels:history`, `channels:read` and `chat:write`. App messages need `im:history` and `im:write`. Agent status needs `assistant:write`. Member checks need `users:read` and `users:read.email`. The Integrations card shows each capability as ready, or names the scopes a reconnect adds. Slack Code is shown as not available yet.

## Connect, reconnect and disconnect

**Add to Slack** and **Reconnect** open Slack, which decides whether the admin may install. Where a Slack workspace requires app approval, a Slack admin approves the app first; a Paws admin role does not bypass that.

- The link works once, for ten minutes, for the admin, session and Paws workspace that started it. On return Paws checks that the person is still an admin before it saves the team, app and bot Slack returned.
- A Slack workspace connects to one Paws workspace. To switch to another Slack workspace, disconnect first. A denial, a failure, or a reconnect that returns another team or app leaves the connection as it was.
- When the setup starts from Slack with that Slack team and, optionally, a channel, Slack offers that team and a successful install returns the admin to the channel, or to the Paws app's messages when no channel was given. Otherwise the admin returns to Integrations.
- **Disconnect** deletes the token and revokes it with Slack. Each change is in the workspace audit.
- When the app is uninstalled from Slack, or Slack revokes its bot token, Paws deletes that workspace's token and records `slack.revoked` in the audit. Other connected workspaces are unaffected, and an event from before the current installation is ignored. Add to Slack connects it again.
- If a rotating token can't be refreshed, the card asks the admin to reconnect.

## Answer in one channel

Paws answers explicit `@Paws` mentions in one internal channel per Paws workspace, in the mention's thread. Once Paws was mentioned in a thread, a linked member's later replies there get answers without `@Paws`, and mean what the same text after `@Paws` means: `stop`, `unlink`, `repo …`, `remember …`, `memory`, `start <TEAM>` and answers to waiting work all work without the mention. It needs no repository and no Linear issue, and a conversation starts no work; only [`@Paws start`](#start-work-from-a-thread) files work. Other channels, edited messages, bot posts, other messages that don't mention Paws and direct messages other than `link <code>` get no answer. An unmentioned reply from someone who isn't a linked member, or in a thread Paws wasn't mentioned in, is ignored without a sign-in link; only a mention sends one.

1. Invite Paws to the channel. The invitation alone changes nothing.
2. Someone mentions `@Paws` there. Paws sends them a direct message from the Paws app with a link to `https://<paws>/oauth/slack/link` for them. When Slack refuses the direct message (for example, their direct messages with apps are turned off), Paws sends the same text as a message only they can see, in the mention's thread.
3. They open that page, sign in to Paws, and get a code. They send `link <code>` to the Paws app in their direct message with it; the page links to that conversation. That links the Slack account that sent it to their Paws account, for the channel they mentioned Paws in. The first person to link must be a Paws workspace admin; their link also sets Paws up in that channel. Paws answers the result, and `@Paws unlink`, in the same direct message.
4. Paws holds the question they asked before linking. When they link within ten minutes of asking it, Paws answers it once, in its original thread, after the same checks as any other mention. Only their latest question is held; an older one, or one asked more than ten minutes before the link, gets no answer. Linking starts no work and grants nothing beyond these answers.

- A code works once, for ten minutes, only when the Slack account it was issued to sends it in its own direct message with the Paws app, in the same Slack installation. Sending it from Slack is what proves the Slack account; Paws links no one from a display name, an email address or who installed the app. Never give a code to someone else. `@Paws link <code>` in a channel thread links nothing and leaves the code unused; Paws asks by direct message for the code there instead. Any signed-in Paws session can open the link page, whether it began from the dashboard or from a Linear sign-in action.
- A Slack account links to one Paws account, and a Paws account to one Slack account, per Slack installation. A code that would move either link is used up and links nothing.
- Connecting Slack again (**Reconnect**, **Add to Slack** after a disconnect, or adopting a `paws login slack` connection) ends the channel setup, every link and every unused code, and Paws drops replies it hadn't posted yet; set up again as above.
- Before each answer and again before posting it, Paws checks that the person is still an active member, the installation is the same and the channel is still internal. A channel shared with another organization, archived or unreachable gets no answer. Setups and links are in the workspace audit as `slack.channel_admitted` and `slack.member_linked`.
- A turn sees the thread's earlier questions from every linked member and the replies Paws posted to them, at most 20 messages, each labelled with who asked. An earlier answer that used channel memory Paws prepared for another member, memory that has changed since, or a repository the asking member can't read or the channel can't see, reaches the turn as its question only. Other threads, other channels and replies Paws never posted are left out; what carries across threads is the [channel memory](#channel-memory). Several messages in a thread are answered at the same time, each with its own reply. A turn also sees the questions posted before its own that Paws is still answering, marked as being answered, as context only; a question from someone who is no longer a linked member, from before the thread's stop, or asked more than ten minutes ago is left out. When more than one person has talked to Paws in a thread, each reply begins with a mention of the person it answers.
- Slack redeliveries of the same mention produce one reply, and Paws posts each reply at most once. Before posting it records the attempt; it retries only when Slack clearly didn't take the message (a rate limit, waiting as long as Slack asks; a Slack server error; or a refused connection). When the outcome is unknown (the connection dropped or timed out after sending, the response was unreadable, Slack answered `fatal_error`, or Paws stopped mid-send), Paws never posts it again: it records the reply as unknown in its outbox and journal, and that reply may be missing. Any other Slack error drops the reply. A model turn interrupted before its reply was recorded runs again, but still produces one reply. Only replies Paws posted, with their Slack timestamp, count as context for later turns.
- Paws answers on the asking member's own paired runner, in its conversation lane, with the workspace's implementer agent. That lane is separate from implementation slots, so answers come even while every slot is busy. The runner must be at version 0.1.94 or newer, online and signed in to that agent. While the lane is full, Paws retries the mention later. When there is no such runner, the lane stays full through the last retry, or the turn times out, fails or comes back empty, Paws posts `I couldn't answer that just now. Ask again in a moment.` in the thread, at most once per thread every 10 minutes; a stopped thread or a member whose link changed gets nothing. The runner sees only the thread's context and, when a repository is attached, the source excerpts Paws read for it; it has no files or tools.
- Paws answers only in public channels. In a private channel it posts nothing, not even setup messages.

### Read a repository

A thread needs no repository. When a question needs code, attach one; Paws then reads it read-only through the GitHub App, without a checkout, a runner slot or a Linear issue, and answers from it.

- `@Paws repo <owner/name> [ref]` attaches a repository to the thread, at a branch, tag or commit, or at its default branch when no ref is given. `@Paws repo off` detaches it. Only a member whose Paws teams can read the repository can attach it; attaching grants no one access. Each thread keeps its own choice, and changing it is always an explicit `repo` command, with or without the mention in a thread Paws was mentioned in.
- `@Paws channel repo <owner/name> [ref]` sets the channel's repository, which threads without their own use; `@Paws channel repo off` clears it. Only a Paws workspace admin who can read it can set it, and the change is in the workspace audit as `slack.channel_repository`. The setting lapses when that admin loses the role or access, and on a reconnect or a move to another channel.
- Before each answer, and again before posting it, Paws checks that the asking member's Paws teams can still read the repository, through their current membership. Without that access Paws doesn't read it and tells only them.
- Whether an answer drawn from a repository's code may reach the channel depends on who can read the channel, not on whether the repository is the channel's or public on GitHub; see [answers drawn from code](#answers-drawn-from-code).
- Paws resolves the ref to a commit for each answer, so a branch follows new commits while a commit stays fixed. The reply names the repository, the commit and the ref it read, and Paws records them with the reply.
- Paws downloads at most four files per answer, binary ones included, and uses at most 4 KB of each, 12 KB in total, chosen by the question's words in their paths, and lists up to 20 matching paths. It skips files over 64 KB, binary files and files named like secrets (`.env`, keys, credentials), and leaves out lines that look like a token or password. Reads are cached per Paws workspace, Slack installation, channel, member, repository and commit.
- An answer that builds on an earlier answer from a repository depends on that repository too, also after `@Paws repo off`. Paws checks every such repository like the attached one, before the turn and before posting, and leaves an earlier answer out of later turns once the member can no longer read its repository.

### Thread notes

Each answer may leave notes for later questions in the same thread, so a follow-up starts from what an earlier answer found out instead of reading the code again.

- Paws asks the agent to end its reply with a block of notes: what it found out, each marked as an observation, a guess or a decision, optionally naming a repository, a file and a symbol. Notes hold no names of people, no secrets and no quoted code. Paws removes the block before posting; nothing of it reaches Slack. A reply without the block, or with one Paws can't read, is posted as usual and leaves no notes. A turn that fails leaves no notes.
- Paws keeps at most 16 notes and 16 KB per answer, each at most 1 KB. A note naming a repository must name one the answer read, and a file it names must exist at the commit the answer read; otherwise Paws drops the note. A note records the commit it was written at and every repository the answer read. The block may add up to 20,000 characters to the agent's reply on top of the answer's own limit.
- A later answer in the thread gets the notes whose repositories its asker's Paws teams can read and may be shown in the channel now ([answers drawn from code](#answers-drawn-from-code)); Paws leaves out the others without saying so. Notes take at most 8 KB of the prompt: notes naming a file or symbol from the question first, then the newest. A note written at another commit than the one this answer reads shows that commit.
- Notes are never merged, edited or deleted. When two disagree, both are shown and the agent is told to check the code.

### Channel memory

Paws keeps a memory for the channel, so a new thread can build on what was decided in an earlier one. It holds only what linked members ask it to keep; Paws doesn't read or import channel history.

- `@Paws remember <text>` stores the text as a fact reported by the member who posted it, not as a settled decision, with the thread, message and time it came from. Paws replies, visible only to them, with the entry's id.
- `@Paws memory` lists up to ten current entries with their ids, visible only to the member who asked. Paws builds the list when it posts it, and posts nothing if that member's link changed in between.
- `@Paws correct <id> <text>` replaces an entry; the old text is kept only as history and is no longer used. `@Paws forget <id>` removes an entry and every summary built from it, also after a restart. Only the entry's author or a Paws workspace admin can correct or forget it.
- Before each answer, Paws adds the entries most relevant to the question to the turn, within a bounded token budget, and folds older entries into a summary when the memory grows past it. The entries are background only: they never approve an action, a tool call, a run or a new issue.
- Memory belongs to the Paws workspace, the Slack installation and the channel's id, so renaming the channel keeps it, while another channel, another Paws workspace or a reconnected installation starts empty. Only linked, active members of the channel's current setup can add to it or have it used for their answers; unlinking, revoking or ending a membership stops that at once.
- An earlier answer in the thread that used an entry since corrected or forgotten is left out of later turns; the question stays.
- When an entry an answer used is corrected or forgotten, or the member's access ends, before Paws posts the answer, Paws withholds it. If that happens before the answer is queued, the member sees a message, visible only to them, asking them to mention Paws again.
- Entries expire after 180 days. Memory needs no runner and starts no work: remembering, listing, correcting and forgetting work while every runner slot is busy, and post nothing beyond the reply to the member who asked.

### Answers drawn from code

On top of the [repository checks](#read-a-repository), Paws checks who can read the channel before it reads a thread's repository, again before it queues an answer drawn from code, and again on every delivery attempt, including a retry after Slack refused it:

- A workspace admin sets, per repository, whether answers drawn from its code may be shared in Slack: `PUT /api/workspaces/slack/disclosure` with `{"repository": "owner/name", "level": "workspace"}`, or `"none"` to stop. `GET` on the same path lists the repositories allowed. Only admins can read or change it, and each change is in the workspace audit as `slack.disclosure_changed`. A repository that isn't listed is shared only through verified access, below, public GitHub repositories included.
- `workspace` allows a channel inside this Slack workspace, public or private, whose members include no guest. Paws reads the channel's flags (`is_private`, `is_shared`, `is_ext_shared`, `is_org_shared`, `is_pending_ext_shared`), its sharing details (`shared_team_ids`, `connected_team_ids`, `pending_shared`, `pending_connected_team_ids`, `context_team_id`) and every member's guest flags. A channel whose details name another team or a pending invitation counts as shared, also for Paws's other answers there. A channel shared across an Enterprise organization, with Slack Connect, or with a pending external invitation is never allowed. A missing flag, a missing scope, an unreadable member or a channel of more than 100 members counts as unverified, and Paws doesn't post the answer.
- Without that policy, Paws shares a repository's code in a public channel only when it can verify everyone who can read the channel: every full member of the Slack workspace and the guests in the channel, through every page of Slack's member lists (`users:read` and `channels:read`, which the app already asks for). Each of them must be linked to Paws in this channel and be an active member whose Paws teams can read the repository. The readership counts as unverified, and Paws shares nothing, when the channel is shared or about to be shared with another organization or workspace (Slack Connect, an Enterprise or org-wide share, a pending invitation), when a member belongs to another Slack team or is missing from the directory, when Slack doesn't say whether someone is a guest or a bot, when another app's bot is in the channel, or when Slack refuses or doesn't finish the member lists. Paws asks Slack again before reading, before queuing the answer and on every delivery attempt, so someone joining the workspace or channel in between withholds the answer.
- An earlier answer that a later turn builds on brings its repository with it, as above, and gets the same checks. An earlier answer whose repository can't be shared in the channel any more is left out of later turns; the question stays.
- When a check fails, Paws doesn't read the repository or post the answer. Instead it posts a message visible only to the person who asked, in the same thread, saying an answer was withheld without naming the repository or quoting anything from it. It opens no direct message and posts nowhere else.

### Start work from a thread

A linked member mentions `@Paws start <TEAM>`, with the key of a Linear team they belong to, such as `@Paws start ENG`. Paws drafts a title, scope and acceptance criteria from the thread on their conversation lane, without channel memory, earlier answers that used it, or an implementation slot, and shows the draft only to them with who can read issues in that team and **Create issue** and **Discard**. Mention `@Paws start <TEAM>` again with what to change, such as `@Paws start ENG: only two retries`, and Paws revises your current draft, if it is less than an hour old, into a new one that replaces it. Each member has at most one open draft per thread: a new `@Paws start` replaces their earlier draft they haven't approved, and while their approved draft is being filed, Paws says so instead of drafting again.

**Create issue** checks the member, team membership, thread and team visibility again, then files one issue in that team, delegated to Paws, with only that title, scope and criteria. The member who started becomes the issue's owner, and the usual Linear intake runs it. A thread can file several issues, one per approved draft; a repeated click or a redelivery files that draft's issue once. After an issue is filed, `@Paws start` in the same thread drafts the next one. Each draft and each chat answer in the thread is told which issues the thread already filed, so the same work isn't filed twice: identifier and title for issues in Linear teams the asking member belongs to, the identifier only for others. Once Paws has tried to file, the approved draft stays bound to the member: after Linear fails to confirm, `@Paws start` files that same draft again rather than a new one, and if the team's visibility changed in between, Paws shows that draft again with the new audience for the member to approve. Other members' clicks, discarded drafts and drafts older than an hour do nothing.

The run gets the thread, up to the `@Paws start` mention and without answers that used channel memory or a repository, as private context. Paws tells the agent not to copy it into Linear, the pull request or commits, and stops giving it once the member who started is no longer an active member of the Paws workspace.

### Work in the thread

Once an issue runs, the thread stays its conversation. Paws posts the run's questions, its progress updates, its replies and problems, and the pull request result in the thread, each starting with the issue's identifier and link, instead of in the issue's Linear session. The Linear session gets only a short note that Paws continued in Slack, so there is one place to answer; the issue, its delegation, workflow state and pull request link stay in Linear as usual. Issues delegated from Linear are unchanged.

- To answer a question or approve a plan, a linked member who can see the work in Paws (on its Linear team, with access to its repository) mentions `@Paws` in the thread with the answer, such as `@Paws uploads`, or replies `uploads` there. When exactly one of the thread's issues waits for an answer, the reply answers it. When several wait, start the reply with the issue key, such as `ENG-2 yes`; any other reply gets `Several issues are waiting: ENG-1, ENG-2. Start your reply with the issue key.` and answers nothing. A reply that starts with the key of an issue that isn't waiting answers no other issue. The first answer resumes the work once; Paws confirms it only to the person who answered, and a redelivered or later mention doesn't answer again. A mention sent before the question was asked doesn't answer it, even when Slack delivers it late, and `@Paws stop`, `unlink`, `repo`, `memory` and `start` keep their meaning.
- An answer from Slack leaves only `Answered in Slack` and a link to the thread in the issue's Linear session, never who answered or what they said. An answer from the Paws dashboard or Linear works too.
- When Paws needs to know which repository the work is in, the thread gets only `Choose the repository in Paws:` with a link to the issue in Paws; the candidates are listed there, never in Slack. Questions Slack can't answer, such as visual reviews, link approvals and GitHub sign-in, post `Answer this in Paws:` with the link. A mention doesn't answer either, and a question that is no longer waiting when its post is due isn't posted.
- Each post needs Slack's channel check to let Paws answer there, and a Paws workspace admin to allow answers from each of the work's repositories in the channel ([Answers drawn from code](#answers-drawn-from-code)). The work's repositories are the one it is bound to or, before it has one, every repository it could be bound to. Work with no repository at all gets only a link to see the update in Paws. The member who started the work must still be linked with the same link, still see the work in Paws and still read its repositories. Otherwise the member who started gets a note, visible only to them, with a link to the issue in Paws; Paws never posts it in Linear or another channel instead.
- A post that was waiting to be sent is dropped when the work is stopped in Paws, Linear or the thread, or restarts. Once Slack is reconnected, the channel changes, or the member who started unlinks, is revoked or links again, the thread gets nothing more.

### Working status and streamed replies

The thread shows Slack's own agent-session status, set with `chat:write`, with no custom loading text. The status only shows what Paws is doing. It never proves that the work or CI succeeded.

- A mention Paws answers shows **processing** from the moment Paws takes it up, before it reads the thread's repository or channel memory, until the last turn running in the thread ends, whether with a reply, a notice, a withheld answer, a stop or an error. Only then does the thread show **active**, or its work's status. While the member's conversation lane is full, the turn keeps the thread **processing** while Paws retries it. A turn counts as ended after ten minutes, so a crash never leaves a thread **processing**. Conversation turns don't wait for implementation slots, so this works while every slot is busy.
- **Create issue** shows **processing** while Paws files the issue. After that the status follows the work, and a thread with several issues shows the busiest of them, so **processing** while any of them runs: **processing** only while it runs, verifies or recovers, **active** while it waits in the queue for a runner slot, for an answer or in the merge queue, **suspended** while paused, and **closed** once it is completed, merged, cancelled or failed. Waiting for a free slot never shows as processing.
- Slack ends **processing** after an hour. Paws sends it again every 50 minutes, only while the work still runs. Paws checks each thread's status once a minute and sends only changes. A status replaced before Slack got it is dropped, so only the latest goes out.
- Replies stream into the thread with `chat.startStream`, `chat.appendStream` and `chat.stopStream`, for the member who asked (`recipient_user_id` and `recipient_team_id`), in bursts of up to 1,000 characters. Paws closes each stream within ten minutes. When Slack rate-limits a burst, Paws waits as long as Slack asks and continues the same stream, also after a restart. When the ten minutes are nearly up, it sends the rest when it closes the stream. A stream Slack has already closed is never restarted. Closing a stream keeps the thread's current status, so a task that still runs stays **processing**. Progress, questions and results of filed work post as separate messages. When several progress updates are waiting, only the latest is posted.
- Status changes and streams pass the same checks as the work's other posts: the member's link, the installation, the channel's audience, task access and the disclosure of the work's repositories. Paws checks again before every burst and before closing a stream. When the member's link, task access, the thread's Stop, the installation or the repository's disclosure changed, Paws closes the stream without adding text. A status or stream from an earlier Slack installation is dropped. Paws records each burst before sending it. When the outcome of a status change or a burst is unknown, including after a restart mid-burst, Paws doesn't send it again and closes the stream without adding text. Slack closes an unfinished stream itself after ten minutes.

### Unlink and revoke

- **Settings › Account** shows your own Slack link, with **Unlink**. Mentioning `@Paws unlink` in the channel unlinks the Slack account that posted it. Either way only your own link ends: the installation, the channel setup and other members' links stay as they are.
- On the Slack card in **Workspace › Integrations**, an admin sees each linked member, marked when their Paws access is revoked, and can **Revoke** a link. Only links in this Paws workspace are listed or changed. Disconnecting the installation stays an admin action on the same card.
- Unlinking or revoking ends the link at once. Paws drops that member's held question and unused link code, stops the turn it is running for them, and withholds replies to them it hadn't posted yet. Their next mention asks them to link again; their unmentioned thread replies are ignored, also when the link ends after Paws received one. Linking again starts fresh: mentions received before the unlink, and replies prepared for the earlier link, are never answered or posted. Paws checks the link once more just before it posts.
- A member whose Paws access is revoked, or whose membership ends, gets no answers and can't stop a thread, even while still linked.
- Unlinking again, or a Slack redelivery of `@Paws unlink`, changes nothing. Each change is in the workspace audit as `slack.member_unlinked` or `slack.member_revoked`, with who made it and which Slack account.

### Threads and Stop

Each thread Paws is mentioned in is recorded once, when the first signed mention from the connected installation arrives: the Slack workspace, installation, channel, thread, who mentioned Paws first and with which event, and the thread Paws replies in. Every later mention, and every later reply from a linked member, in the thread is stored with the Slack user who posted it. An unmentioned reply never records a thread. When a reply mentions Paws, Slack delivers it twice, as a mention and as a message; Paws answers it once. The record grants nothing: each answer still needs the checks above. Slack redeliveries, including one after Paws stored a mention but before Slack saw the answer, are acknowledged and produce no second turn.

A linked member mentions `@Paws stop`, or replies `stop`, in the thread to stop it. Paws records the stop when the mention arrives, without waiting for a runner, so it works while every slot and the conversation lane are busy. It ends the turn that is running within about a second, never posts a reply to any mention made before the stop, and ignores a delayed delivery of one of those mentions. The member who stopped it sees a message only they can see. A mention after the stop starts a new turn. A stop from someone who isn't linked is treated as any other mention.

Each reply and work post Paws posts has a **Stop** button. A click from a linked member stops the thread the same way, from the moment of the click, also while every slot and the conversation lane are busy. Paws checks each click's Slack signature, its age (at most five minutes) and that it comes from the connected Slack workspace and app; anything else is refused or ignored. Each click is stored, and one click per button counts: clicking the same button again, or Slack delivering it twice, has no further effect. A click from someone who isn't linked does nothing and doesn't use up the button. Slack's own stop control for the thread's agent session (`agent_session_stopped`) counts as a click from the person who used it, in a thread Paws was already mentioned in.

In a thread whose work was filed from it ([Work in the thread](#work-in-the-thread)), a stop also stops each of its issues whose work the person may stop: the member who started that work, or a Paws workspace admin, when that person can see it in Paws as the dashboard's **Stop** requires. Paws stops it once, as **Stop** in Paws does (when the stop comes while the issue is being filed or before Paws has picked it up, it waits up to a day for it and then stops it), and the pull request, if there is one, stays open. Updates queued before the stop arrived that Paws hadn't posted in the thread yet, including ones still waiting to go out to Linear, are dropped, also when the work had already finished; posts that come after the stop, such as a later merge, still arrive. The person who stopped sees a note only they can see, and the stop is in the workspace audit as `execution.stop`. A stop from any other linked member stops only Paws's answers to mentions. `@Paws stop ENG-1`, or the reply `stop ENG-1`, stops only that issue's work, under the same rule, and leaves the thread's answers and its other issues running. A stop also reaches an issue Linear filed without confirming it, and `stop ENG-1` sent before Paws has picked up ENG-1 waits for it like a plain stop. Redeliveries, a second stop and a restart of Paws stop nothing again; a stop whose member unlinks or loses access before Paws carries it out stops nothing, and the work in other threads is never affected.

`paws doctor` checks each connected Slack workspace: channel threads need the scopes above, and a missing one fails with a reconnect hint. App messages and agent status are shown as optional notes, and Slack Code is shown as not available; neither stops channel threads from working.

## Use a `paws login slack` connection

`paws login slack` connects Slack to the server rather than to a Paws workspace. When such a connection exists and the Paws workspace has none, the Integrations card offers **Use the paws login slack connection**. It moves that token, with the scopes it already has, into the admin's Paws workspace and removes the server-wide copy, without opening Slack or asking for new permissions. Paws refuses when the workspace is already connected, the Slack workspace belongs to another Paws workspace, the token rotates, or it was issued to an app other than `SLACK_APP_ID`. The move is recorded in the workspace audit as `slack.adopted`.
